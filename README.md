## 📖 О проекте

**MoveIT service** — полнофункциональное веб-приложение для управления
материально-техническими ресурсами (ТМЦ) организации. Включает:

- иерархический **справочник** категорий и типов;
- **две модели хранения**: склады с адресным хранением (Склад → Зона →
  Стеллаж → Ячейка) и рабочие места (Офис → Кабинет → Место);
- **5 статусов техники**, включая `placed` — «на рабочем месте»;
- **«виртуальные склады»** `maintenance` / `retired`;
- **серверный фильтр и поиск** на странице техники;
- **карточку техники** с двухколоночным layout и действиями;
- компактные формы с **живым предпросмотром**;
- полную **инвентаризацию** со сводками и экспортом в CSV.

### 🎯 Для кого

- **Малый и средний бизнес** — учёт ноутбуков, телефонов, офисной техники
- **IT-отделы** — управление парком устройств сотрудников
- **Отделы снабжения** — контроль выдачи и возврата ТМЦ
- **Образовательные учреждения** — учёт оборудования

### 🎛️ Действия с техникой (этап 4.2)

Все действия — из карточки (клик по строке в `/manage`):

- **📦 На склад** — разместить в ячейке.
- **🔄 Переместить (склад)** — в другую ячейку.
- **🪑 На рабочее место** — привязать к месту.
- **🔄 Переместить (место)** — сменить место.
- **👤 Назначить** — выдать пользователю.
- **🔧 В ремонт** — перевести в `maintenance`.
- **❌ Списать** — перевести в `retired`.
- **↩️ Вернуть** — вернуть на склад.
- **↩️ Вернуть в эксплуатацию** — из `maintenance` / `retired` в `available`.
- **✏️ Редактировать**
- **🗑️ Удалить**

Действия доступны **admin / mol** (mol — только на своей технике).
**Supervisor** — только просмотр.

### 🧑‍💼 Материально ответственные лица (МОЛ)
- МОЛ за склады (`warehouse_responsibles`)

- Фильтрация на уровне SQL

### 🧩 Номенклатура (модели ТМЦ)
- Модель (`equipment_models`) — обобщённое описание
- Экземпляр (`equipment`) — конкретная единица
- Категория и тип — на модели
- Страница `/admin/models` — CRUD моделей
- Просмотр: admin / supervisor / mol
- Создание / редактирование: admin / mol
- Удаление: только admin

### 📥 Импорт из CSV

Страница `/manage/import` (только admin) — загрузка номенклатуры
и экземпляров из CSV-файлов 1С.

- **Формат:** `Корпоративный ИД;Наименование;Производитель;Группа;Вид;Инвентарный номер;Конечный остаток;Описание`.
- **Кодировка:** Windows-1251 (по умолчанию) / UTF-8 / авто.
- **Разделитель:** `;` / `,` / `\t` (табуляция).
- **Заголовки:** автоопределение (русские / английские алиасы),
  либо стандартный порядок колонок.
- **Парсер с кавычками** (RFC 4180) — значения в кавычках могут
  содержать `;`, `,`, `\n`, `""`.
- **Категории / типы / модели** создаются автоматически, если их нет.
- **Предпросмотр** — первые 5 строк + прогноз изменений в БД.
- **История импортов** — последние 20, с отменой по `import_id`.
- **Ответственный МОЛ** — выбирается в форме импорта.
- **`quantity > 1`** — создаётся N экземпляров без `inventory_number`.
- **Дубликаты без номеров** — пропускаются (галочка).

### 🏢 Склады и адресное хранение
- 4-уровневая иерархия: Склад → Зона → Стеллаж → Ячейка
- Склад по умолчанию
- **Дерево структуры** склада:
  - разворачивание зон → стеллажей → ячеек
  - CRUD на каждом уровне
  - кнопки «Развернуть всё» / «Свернуть всё»
- Просмотр ячейки
- Флаг `is_full` и `capacity`
- `checkCellAvailability` — единый хелпер
- Перемещение техники
- Ответственные МОЛ (только для admin)
- Доступ: admin / supervisor / mol
- **Автозаполнение ячейки** при создании:
  - название — «Ячейка N» (N = количество + 1);
  - код — из названия стеллажа (например, «Стеллаж А-04» → `А-04-01`).
- **Массовое создание стеллажей** — поле «Количество стеллажей» (1..N) в модалке.
- **Автосоздание ячеек при создании стеллажа** — поле «Создать ячеек» + автогенерация кодов.
- **Описание стеллажа** — выводится в дереве склада.

### 🏛️ Рабочие места
- 3-уровневая иерархия: Офис → Кабинет → Рабочее место
- Офис по умолчанию
- **Дерево офиса** с разворачиванием кабинетов и мест
- **Описание места** — выводится в дереве под названием.
- **Автозаполнение названия и кода** при создании места (как у ячеек).
- **Описание места в селекте «Переместить на рабочее место»**.
- Привязка техники
- Ответственные МОЛ
- Доступ: admin / supervisor / mol

## 🎭 Роли и права

В системе **4 роли**: `admin`, `supervisor`, `mol`, `user`.

### 👑 Администратор (role: admin)

Полный доступ: пользователи, справочники, склады, офисы, техника,
логи, управление МОЛ.

### 👁️ Супервизор (role: supervisor)

Read-only ко всему, кроме логов. Директор / бухгалтер / аудитор:
видит статусы, места, назначения, пользователей, но **ничего
не может менять**. Логи скрыты.

### 🧑‍💼 МОЛ — материально ответственное лицо (role: mol)

Работает только со «своим»:

- **Свои склады** — через `warehouse_responsibles` (many-to-many);
- **Свои офисы** — через `office_responsibles` (many-to-many);
- **Свои экземпляры** — те, где `equipment.responsible_user_id = он`.

**Может:** редактировать свои склады / офисы, удалять пустой свой склад,
добавлять и редактировать свои экземпляры, перемещать их, назначать
пользователям, добавлять модели.

**Не может:** видеть чужие склады / офисы / экземпляры, управлять
пользователями, удалять модели и справочники, назначать МОЛ,
видеть логи.

### 👤 Пользователь (role: user)

Только `/profile` (своя техника, история, смена пароля) и `/pdf`.

  экземпляр, роут вернёт 404 (не палим существование)

  доступа к складам / офисам / экземплярам
- **`routes/admin-responsibles.js`** — управление МОЛ (привязка
  к складам / офисам / экземплярам)

## [3.1.0] - 2026-10-13

**🎉 Этап 3.3 завершён: разделение «модель ТМЦ» / «экземпляр ТМЦ»**

Мажорный минорный релиз, закрывающий крупную переработку модели
данных. Введена таблица `equipment_models` — обобщённое описание
устройства (название, производитель, категория, тип). Таблица
`equipment` стала «экземпляром», ссылается на модель через
`model_id` и хранит только атрибуты конкретной единицы
(`inventory_number`, `serial_number`, `status`, место хранения,
даты, описание).

Подшаги 3.0.1 – 3.3.5 (теги v3.0.1 – v3.0.8).

### Итог этапа

- **Все модули БД** читают данные техники через `JOIN equipment_models`:
  `equipment.js`, `stats.js`, `dashboard.js`, `warehouses.js`,
  `workplaces.js`, `profile.js`, `users.js`, `catalog.js`.
- **Все роуты** работают с новой схемой: `admin.js`, `equipment.js`,
  `dashboard.js`, `profile.js`, `users.js`, `catalog.js`.
- **Формы** `/admin/add` и `/admin/edit/:id` — селект модели ТМЦ
  + кнопка «Создать модель» + живой предпросмотр.
- **UI**: таблицы `/admin`, `/equipment`, `/admin/catalog`, `/profile`,
  `/users` — колонки «Модель | Corporate ID».
- **Карточки**: техники (admin, catalog, equipment), пользователя
  (admin), профиля — все поля из модели.
- **Страница `/admin/models`** — полноценный CRUD моделей
  с карточкой экземпляров.
- **Программная уникальность** `inventory_number` / `serial_number`
  (`checkUniqueSerialAndInventory`) — с понятными ошибками.
- **Seed** создаёт модели + экземпляры; `description` — на модели.
- **Migrate** идемпотентна.

## [3.0.8] - 2026-10-13

**🌱 Seed моделей ТМЦ + идемпотентность migrate + профиль**

Подшаг 3.3.5. Seed приведён к новой модели данных: создаются
модели ТМЦ и экземпляры, `description` переехало на модель.
Миграция стала идемпотентной — повторный запуск не падает
на уже пересозданной `equipment`. Карточка профиля дочищена —
активная техника и история работают через `model_name`.

## [3.0.6] - 2026-10-13

**🔧 Дашборд и агрегаты: JOIN с `equipment_models` во всех модулях**

Подшаг 3.3.4. Завершён перевод всех модулей и роутов, работающих
с техникой, на новую модель данных. Дашборд, инвентаризация
складов, рабочие места, профиль и карточка пользователя больше
не обращаются к несуществующим полям `equipment.name`,
`equipment.model`, `equipment.manufacturer`, `equipment.category_id`,
`equipment.type_id`.

## [3.0.4] - 2026-10-13

**🧩 Переход техники на `model_id` — модуль БД, роуты, формы**

Подшаги 3.3.1 – 3.3.2. Единый переход экземпляров ТМЦ на новую модель
данных «модель ТМЦ / экземпляр ТМЦ». Роуты и формы больше не работают
со старыми полями `equipment` (`name`, `model`, `manufacturer`,
`category_id`, `type_id`) — эти данные живут в `equipment_models`
и читаются через JOIN.

## 🔒 Безопасность

### Реализовано

- ✅ **Хеширование паролей** — bcryptjs, 10 раундов
- ✅ **Сессии** — httpOnly cookies, SameSite=Lax
- ✅ **Проверка на каждом запросе** — `syncSession`:
  пользователь существует, активен, роль совпадает,
  логин совпадает, версия БД совпадает
- ✅ **Транзакции** при удалении пользователя
- ✅ **Защита от self-delete**
- ✅ **Защита последнего админа**
- ✅ **Защита связанных данных** (категории/типы, склады, места)
- ✅ **XSS-экранирование** — escapeHtml / escapeAttr
- ✅ **Логирование** всех действий
- ✅ **Валидация** логина, email, пароля
- ✅ **Валидация статус ↔ место** на сервере и клиенте

### Рекомендации для production

1. **Смените SESSION_SECRET** в `.env`:
   ```bash
   node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
   ```

2. **Включите HTTPS** и установите `cookie.secure = true`
3. **Настройте reverse proxy** (nginx, Caddy)
4. **Ограничьте доступ к БД**
5. **Регулярные бэкапы** `data/database.db`
6. **Rate limiting** для `/api/auth/login`
7. **Обновляйте зависимости** — `npm audit fix`
