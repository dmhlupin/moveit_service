## 2026-10-26 /admin/catalog — серверный рендеринг таблицы техники
**Что делал:** закрывал 5.11.3 (карточка техники через `EquipmentCard`),
разбирался с рассинхроном scope (`getFilteredEquipmentAPI` не передавал
`scope` в `getEquipmentWithLocation`, под МОЛом таблица отдавала чужую
технику, которая не открывалась в карточке).
**Что неудобно:** таблица техники на `/admin/catalog` рендерится
**на клиенте** (`renderEquipmentTable` в `catalog.js`, ~250 строк:
таблица, пагинация, поиск, фильтры). Дублирует серверный рендер
`equipmentRows` из `renderManage`. Логика «что показывать» (статусы,
владелец, ответственный МОЛ, права) — в двух местах, рассинхрон уже
стрелял (scope). Под серверный рендер нужно: `{{equipment_rows}}`,
`{{pagination}}`, `{{filter_category_options}}`, `{{filter_type_options}}`,
`{{filter_search}}` в шаблоне + чтение `req.query` в `renderCatalog`
(category_id / type_id / search / page) + `getEquipmentWithLocation(filters, scope)`
+ `renderManagePagination`-подобная пагинация. `getFilteredEquipmentAPI`
можно удалить (или оставить для совместимости). `catalog.js` сократится
на ~250 строк — останутся только категории, типы, модалки CRUD,
`openEquipmentCardCatalog`.
**Идея:** отдельный подэтап **5.11.6 / 5.12** — «`/admin/catalog` на
серверный рендер по аналогии с `/manage`». Фильтры (категория/тип) и
поиск — через `location.href` с query-параметрами (перезагрузка ок:
фильтры редкие, поиск редкий). Карточка техники (`EquipmentCard`) —
уже работает, ничего не трогаем.
**Приоритет:** средний (чистота слоёв + устранение дубля; UX не страдает —
перезагрузка при смене категории/поиске приемлема).
**Статус:** запланировано на 5.11.6 / 5.12.

## 2026-10-26 /admin/catalog — ступень «Модель» в иерархии
**Что делал:** смотрел `/admin/catalog` после 5.11.3 / 5.11.4a
**Что неудобно:** в справочнике иерархия **Категория → Тип → (пропуск) →
Экземпляры**. Ступень **«Модель ТМЦ»** (`equipment_models`) — пропущена,
хотя она есть в БД и используется везде (экземпляр ссылается на
`model_id`). Получается нелогично: категории и типы видны, экземпляры
типа видны, а модели — нет. При этом модели управляются **отдельной
страницей** `/admin/models` («Номенклатура»), которая по смыслу — часть
того же справочника.
**Идея:**
1. Добавить **третью ступень** в `/admin/catalog`: после выбора типа —
   список **моделей** этого типа (с количеством экземпляров), клик по
   модели → таблица экземпляров **только этой модели**.
2. **CRUD моделей прямо в `/admin/catalog`** (создание / редактирование /
   удаление), по аналогии с категориями и типами (модалки, `POST/PUT/DELETE`).
   API моделей уже есть (`/api/admin/models` — 6 эндпоинтов, `routes/equipment-models/`),
   переиспользовать.
3. После этого **страница `/admin/models` («Номенклатура») не нужна** —
   весь справочник в одном месте: **Категория → Тип → Модель → Экземпляр**.
   Пункт «Номенклатура» убрать из sidebar (или оставить как алиас
   `/admin/catalog?view=models` — решить при реализации).
4. **Названия:** если `/admin/models` убираем, «Классификация» и
   «Номенклатура» сливаются в один раздел. Варианты: оставить
   «Классификация» (текущее имя sidebar), или переименовать в
   «Номенклатура» (шире по смыслу — покрывает и категории, и типы,
   и модели). Решить при реализации.
**Приоритет:** средний (UX-логика; модели уже управляются, но в
отдельном месте — не критично, но «правильнее» свести в один справочник).
**Зависимость:** логично делать **после** 5.11.6 (серверный рендер
`/admin/catalog`), потому что третья ступень + фильтр по `model_id` —
это те же `req.query` / `getEquipmentWithLocation` / серверный рендер.
**Статус:** запланировано (5.12+).

**Важный опыт:** `db.backup()` в `sqlite3` 5.x на Windows создаёт
**0-байтные** файлы (баг пакета). Использовать **`VACUUM INTO`** —
штатный и кроссплатформенный способ консистентного бэкапа SQLite 3.27+.
